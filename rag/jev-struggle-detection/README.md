# Jevによるcoding agentの苦戦判定: 調査メモ

出典: [Wink](https://arxiv.org/html/2602.17037)、[Graphectory](https://arxiv.org/html/2512.02393)、[CLI coding agentの失敗過程](https://arxiv.org/html/2607.09510)、[The Intervention Paradox](https://arxiv.org/html/2602.03338)、[TypeSafeのNoul](https://docs.typesafe.ai/primitives/noul)・[state](https://docs.typesafe.ai/concepts/state)・[skill suggestion](https://docs.typesafe.ai/cookbooks/skill_suggestion)・[RAG候補判定](https://docs.typesafe.ai/cookbooks/classifying_rag_passages)・[モデル制約](https://docs.typesafe.ai/model-jaggedness/jev-1.13)、[一次資料の原文抜粋](raw/primary-excerpts.md)  
取得日: 2026-09-23  
確度: 一次資料の内容は直接確認済み。Caveatへの適用は未検証の設計仮説。Grokの調査を照合済み。

## 分かったこと

- **「エラーあり」は苦戦の定義にならない。** CLI coding agent 1,794実行の研究では、成功した実行の71%にも途中のエラーがあった。失敗後に問題を認識し、診断を変え、回復したかが重要。明示エラーのない誤前提もある。同研究の失敗原因では、既存情報の誤用など認識上の誤りが57.9%、知識不足が24.0%だった。したがって、苦戦を検知しても常に知識検索が適切とは限らない。
- **経過を見る価値はあるが、反復自体も確定証拠ではない。** Graphectoryは停滞・同じ行動の循環と介入を調べ、問題のある86実行で解決率がモデル別に6.9〜23.5ポイント上がった。一方、難しい課題や強いモデルは文脈収集・試行も増える。単純な回数だけを失敗に変換できない。
- **短い介入の可能性には実証がある。** MetaのWinkは作業軌跡から問題種を判定し、非同期にsystem-reminderを入れた。15日間の本番A/Bで失敗したtool callは相対4.2%、セッションあたりtokenは5.3%、技術者の介入は4.2%減った。報告された90.93%の回復は、介入が一回のケースをLLM judgeで事後判定した値であり、全作業の成功率ではない。Caveatの知識検索介入についての直接の証拠でもない。
- **判定が当たっても介入が有益とは限らない。** The Intervention Paradoxでは、失敗予測のAUROCが0.94でも、実行途中の警告・巻き戻しで成功率が最大26ポイント下がった設定があった。Caveatの短い知識通知とは介入の中身も課題も異なるが、「苦戦判定精度」だけを採用基準にできない。TypeSafeのskill suggestion実例でも、誤ったskill選択は16.8%から7.3%へ減った一方、315件中7件は提案によりagentが独力で正しく選べたskillを誤った。
- **早期予知は難しい。** CLI研究のprefix監視器は、ロックイン後の判定精度82%でも、事前警告は失敗の3.7〜8.7%、実時間の再現率は最大28.8%だった。目標の要件を渡すと一部の分類が改善した。早い段階から全ての苦戦を見抜くという期待は置けない。
- **Jevは狭い判断に向くが、この用途の精度は未実証。** TypeSafe公式はNoulを単一のyes/no判断に使い、確率の閾値を用途のデータで校正するよう案内する。無関係な長いstate、敵対的な文面、日本語を含む非英語文脈には精度面の注意がある。Jevが自然文の要約や新しい検索クエリを生成する製品ではない。

## Caveatへの設計仮説

1. 既存の失敗・再試行・再編集などは、Jevを呼ぶ候補を絞る**観測値**にする。Caveatが最新の依頼、未解決のエラー、対処、検証結果を原文のまま選んでstateに渡す。全sessionや全知見DBは送らない。
2. Jevへの質問は分ける。例: 「同じ問題への対処が続き、まだ進展していないか」「この時点で知識の検索が次の一手として役立つか」。後者が真でも候補がなければ、検索を促す。候補があれば、Caveatが先に検索し、Jevに「この知見は現在の具体的な問題に適用できるか」を候補ごとに問う。
3. 通知はセッション内の新しい問題や新しい知見だけにし、同じ件数増加を再通知しない。既存計画のsidecar廃止・重複削減はJev採否と独立に扱う。

Grokには独立に同じ問題を調べてもらった。Grokの結論は「Jevは候補再評価に絞り、苦戦判定には使わない」だった。予測と介入の効果を区別する指摘は一次資料で確認できた。一方、TypeSafeの[公式説明](https://docs.typesafe.ai/introduction/coding-agents)が否定するのはJevをcoding agentの会話モデルに置き換えることであり、限定した状態に対する苦戦のyes/no判断自体を禁じてはいない。したがって苦戦判定への利用は棄却も採用も確定せず、候補再評価と分けて実測する。

## 採否を決める実測

- 過去のClaude/Codex記録から、その時点までの文脈だけを切り出す。正常探索、単発失敗からの回復、進展のない反復、知識不足、誤前提、外部環境障害、手順確認を含めて人が「いま検索を促すと有益か」をラベル付けする。最終的な成功/失敗を全途中時点へ貼り付けない。
- 現行の構造的ゲート、重複削減後のゲート、Jevを追加したゲートを同じ事例で比較する。介入すべき時点の再現率と誤通知率、最初の有用な通知までの遅れ、適切な知見の上位候補到達率、注入文字数、hook遅延、API入力token、日本語例と英語例の差を見る。候補検索の取りこぼしとJevの判断ミスを別に集計する。
- liveでの有用性は、最初は表示しないshadow判定で確認する。通知を始めるなら、実際に調査へ移ったか、問題を解決したか、無関係な介入を受けたかを別に測る。論文の改善率をCaveatの期待値として流用しない。

この時点では研究と設計仮説だけ。Jevの実APIによる苦戦判定、Caveatの実sessionでの精度、外部APIへ送るprivate情報の範囲は未検証。
